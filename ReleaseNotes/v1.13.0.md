# ECGrav 1.13.0 — a run now records where every configuration was

Parallel tempering is only worth its cost if configurations actually travel from the hot end of
the ladder to the cold end and back. `HomogeneousHamiltonian.md` §7 has said so since 1.11.0 —
*judge it by round trips, not swap acceptance* — and nothing in the package computed them.

This release makes that measurable, and adds the tooling to read it.

---

## ⚠️ Read before upgrading

**One breaking change, and it is narrow.** Beta-schedule chart rows are no longer flattened. The
observables used to be spliced into the row; they are now a single nested column:

```wl
chart[[…, 4 ;;]]     (* before: observables, spread over columns 4 onwards *)
chart[[…, 4]]        (* now:    the observable list, one column           *)
```

**Energy is still column 3** in every layout, which is the only column the package itself reads
out of a beta chart, so `ComputeMinusBetaTimesFreeEnergy[chart[[All, All, 3]]]` and every energy
read are unaffected. If your notebooks do not index a beta chart past column 3, nothing changes
for you.

**No numbers change.** Nothing in the sampling, the reweighting or the free-energy solve was
touched. Runs already on disk stay readable, and every analysis tool here works on them.

Requires Wolfram Language 15.0+, unchanged.

## Round trips, and everything needed to count them

### The chart records the permutation

Both chart layouts now carry a configuration tag — which configuration occupies which slot, at
every sweep — read immediately after the swap step:

| layout | row |
| --- | --- |
| external field | `{sweep, c, energy, conjObs, residual, {obs…}, tag}` |
| beta schedule | `{sweep, beta, energy, {obs…}, tag}` |

The value was already being maintained internally; it simply was not written down. Because the
swap step exchanges a *matching* of non-intersecting edges, a configuration moves at most once per
sweep, so this column is a complete trajectory at sweep resolution — and unlike the swap
histories, it carries **dwell times**.

That is also the reason the beta row had to be unflattened. Splicing the observables put every
column after the third at a position depending on how many observables the caller passed, so no
fixed-position column could follow them. The tag was not merely inconvenient to add there; it was
impossible.

### `TemperingMixing.wls`

New, with `TemperingMixing.md`. Round trips per configuration, the replica flow, occupancy,
swap-graph connectivity and the acceptance profile, from the return of `GraphParallelTempering` or
`GraphCTLSchedule`:

```wl
mix = TemperingMixing`MixingData[res];
TemperingMixing`MixingReport[mix]
TemperingMixing`MixingPlots[mix]
```

**It works on runs made before this release.** Those have no tag column, so the trajectories are
reconstructed from the swap histories instead — exactly, not approximately. The two records
cross-validate on any run carrying both.

The document is in two halves. The physics: why swap acceptance is necessary and not sufficient,
why the round-trip count rather than `numsweeps/corrT` is what sets the real sample size at the
cold end, and what a flat stretch in the replica flow tells you. Then the implementation, which
turns on a fact worth knowing before reading any of this data — the swap history holds **not a
trajectory** but the ordered list of configuration tags that occupied each slot.

## `corrTMeasured` was lying to you

The overload of `GraphComputeCorrelationTime` that every external-field tempering run goes through
initialised the flag to `False` and never assigned it. So every replica of every such run reported
that its correlation time had never been measured — sitting next to `corrTValues` holding
integrals in the hundreds.

The flag exists to separate a `corrT` of 2 that was *computed* from one that fell back to the
floor. It now does that in all four overloads. **No number changes**; the flag tells the truth.

If you have runs on disk with `corrTMeasured -> False` everywhere, that is this bug, not a
diagnosis — read `corrTValues`, which was always correct.

## Plotting

`TemperingPlots.wls` and `TemperingPlots.md`, added in this release, turn a run into continuous
surfaces over $(\beta, n_{t0})$ — free energy, internal energy, heat capacity, and any observable,
with the per-replica values overlaid.

Everything is computed in one batched pass. MBAR weights do not depend on the observable, so one
weight matrix serves every surface, and the whole grid is a single matrix product rather than one
per point. Measured on a $K = 16$, $N = 800$ run over a $12\times12$ grid: **15.3 s for 13
surfaces became 0.076 s for all 52**, needing no parallel kernels. Agreement with the per-point
route is between `0` and `2.7e-11`.

It requires 1.11.0 or later and says so if it is not there: below that the private MBAR helpers do
not exist, and an undefined private symbol returns *unevaluated* rather than failing, so every
surface silently produces nothing.

## Documentation corrections

**`HomogeneousHamiltonian.md` §8 claimed the effective-sample-size mask keeps replicas inside the
region the bootstrap actually sampled. It does not.** Measured on a $K = 16$ run covering
$n_{t0} \in [-1, 1]$, handed its own bounding box: **seven of sixteen replicas landed outside that
range**, out to $|n_{t0}| = 2.29$. The mask measures how concentrated the MBAR weights are, not how
far the target is from the sampled set. §8 now says so and gives the inscribed-box recipe that does
work; §9 no longer presents 1.10.1's defect D as a complete fix.

**§7.1's masking template was not usable as written** — its `If` had no third argument, so the
sampled region returned `Null`.
