# ECGrav 1.9.1 — the empty complex had no Euler characteristic

`EulerChi[{}]` returned `$Failed` with `EulerChi::argerr` instead of 0.

Bug fix only. **No public function was removed, no argument order changed, no new setting**, and
no result that previously computed changes value. Requires Wolfram Language 15.0+, unchanged.

---

## ⚠️ Read before upgrading

**This affects you if any of your energy callbacks take the link of an edge** — the induced
subgraph on the common neighbourhood of two vertices. That slice is `{}` whenever the two
vertices share no neighbour, and on a sparse graph that is most pairs: on 12 vertices with 18
edges, 32 of the 66.

The failure is loud rather than silent — an unevaluated expression where a number belonged, and a
stream of `EulerChi::argerr` — so there is no quietly-wrong past result to distrust. But it can
surface a long way from its cause: the bad value propagates into whatever arithmetic consumed it,
and a Monte Carlo driver will go on to do Metropolis with a non-numeric energy delta.

If your runs have been completing and returning numbers, you were never hitting it.

---

## What went wrong

`EulerChi` dispatches on three patterns, two of which gate on `Depth`:

```wl
EulerChi[facetsLst_List /; (Depth[facetsLst] == 3 && Max[facetsLst] > 1)]
EulerChi[Amat_List     /; (Depth[Amat] == 3 && Max[Amat] <= 1)]
EulerChi[g_Graph]
```

`Depth[{}]` is 2, so the empty list matched none of them and fell through to the catch-all. The
irony is that the convention was already implemented: `EulerChiAM`, which the adjacency overload
delegates to, opens with `If[n == 0, 0, ...]`. Nothing could reach it.

### How it shows up

Code that computes how a quantity changes when edge `(i,j)` is toggled evaluates the link:

```wl
sphInt = Flatten[Position[am[[i]]*am[[j]], 1]];   (* common neighbours of i and j *)
s*(EulerChi[am[[sphInt, sphInt]]] - 1)
```

When `i` and `j` share no neighbour, `sphInt` is `{}`, `am[[{}, {}]]` is `{}`, and the whole
expression came back as `-1 + $Failed`.

A reported `GraphCTLSchedule` run died exactly this way. Two things let it through:

- **A spot check on one pair passed.** Whether one particular pair has a common neighbour is close
  to a coin flip at these densities, and the pair that was checked happened to have one.
- **The `DelHUsableQ` gate passed.** It probes `dH[seed, 1, 2]` — a single pair, on the seed graph.
  It is built to catch a malformed callback, and cannot see a failure that depends on which pair
  and which state.

---

## The fix

```wl
EulerChi[{}] := 0
```

The empty complex has no simplices, so its alternating sum is empty.

Matched as a literal rather than by widening either `Depth` guard, so the three existing overloads
are untouched. `{}` reads as either an empty facet list or an empty adjacency matrix; both denote
the empty complex and both give 0, so one definition serves both readings.

`EulerChi::argerr` also named only the facet-list form while the function accepts three; it now
names all of them, and the usage message documents the `{}` convention.

---

## How this was verified

- The **link-of-an-edge identity**, which is the route that reaches the empty case: toggling edge
  `(i,j)` changes the Euler characteristic by `chi(link) - 1`. Across 40 random 8-vertex graphs —
  **1120 toggled pairs, 302 of them with an empty link** — that agrees with recomputing
  `chi(new) - chi(old)` in every single case. This checks the incremental formula, not merely that
  the error stopped.
- All three existing overloads still route correctly (facet list, adjacency matrix, `Graph`
  object, and the `1x1` matrix), and the catch-all still fires on genuinely bad input.
- The new test was run against the unfixed code, where it fails.

The suite is at **186 tests**, all passing.

PacletInstall["/path/to/ECGrav-1.9.1.paclet"]
