# ECGrav 1.14.0 — two observables that were silently wrong when misused

The combinatorics work coming next measures connectivity, dimension and Betti numbers on random
pure complexes. Auditing the functions that compute them turned up something worth a release: the
functions are all correct, and **three ways of calling them return a plausible wrong number with no
message**. Two are now guarded at the source; the third is documented.

None of this was found by a failing test. Every one of these functions passed everything it had —
because what was wrong was the calling convention, and a wrong convention does not raise.

---

## ⚠️ Read before upgrading

**`CountHoles[c, k]` returns a different number than it did.** It was `BettiNumbers[c][[k]]`, and
that vector starts at `b_0`, so the two-argument form returned `b_{k-1}` — one below the index
asked for — while its usage message promised "the number of k-holes, i.e. the k-th Betti number".

```wl
CountHoles[tetrahedronBoundary, 1]
(* before: 1  -- b_0, the number of connected components *)
(* now:    0  -- b_1, the number of independent loops    *)
```

`k` is now the topological dimension of the hole, counted from 0: `CountHoles[c, 0]` is the
component count, `CountHoles[c, 1]` the loop count, `CountHoles[c, 2]` the number of enclosed
voids. The boundary of a tetrahedron gives `{1, 0, 1}`.

**Both readings produce small plausible integers**, which is why this could never surface as an
obvious failure — a figure labelled `b_1` would have been plotting `b_0`. **Re-run any saved
analysis that calls the two-argument form.** The one-argument `CountHoles[c]`, which returns the
whole Betti vector, is unchanged and is the safer call.

An out-of-range `k` now reports `CountHoles::badk` instead of leaking an unevaluated `Part`
expression.

**`FractionInLargestComponent` no longer accepts a facet list.** It takes a graph or an adjacency
matrix, and it used to reach `AdjacencyGraph` with no validation. A pure complex's facet list is a
rectangular array, and it is *square* whenever the facet count equals the purity — so it was
accepted as a weighted adjacency matrix:

```wl
FractionInLargestComponent[{{1, 2, 3}, {4, 5, 6}, {7, 8, 9}}]
(* before: 1        -- read as a 3x3 weighted adjacency matrix, which is connected *)
(* now:    $Failed  -- with FractionInLargestComponent::notadj *)
```

Three disjoint triangles have 3 of 9 vertices in the largest component; the answer is `1/3`.
Non-square facet lists already failed loudly, so **only the M = p case was silent — and a sweep
over the facet count reaches it every time**. Convert first:

```wl
FractionInLargestComponent[GraphFromCliques[complex]]   (* 1/3 *)
```

The same guard applies to `FractionInLargestKPathComponent`. Genuine adjacency matrices are
unaffected.

**No other numbers change.** Nothing in the sampling, the reweighting, the free-energy solve or any
Monte Carlo driver was touched. Requires Wolfram Language 15.0+, unchanged.

## The third trap, documented rather than guarded

`FacetAdjacencyMatrix` is **not** an adjacency matrix despite the name: it returns facet sizes on
the diagonal and `|facet_i ∩ facet_j|` off it. `SpectralDim` accepts it without complaint and
returns a plausible, meaningless number — 2.516… on the boundary of a tetrahedron. To get the dual
graph, threshold it first:

```wl
Boole[Map[# == p - 1 &, fam - DiagonalMatrix[Diagonal[fam]], {2}]]
```

Also worth knowing before reporting a dimension: **`SpectralDim` at a fixed step `s` is a local
probe, not an asymptotic dimension.** On a cycle graph it returns the same value at n = 20, 60 and
150, because a 6-step walk cannot see the global structure. That is correct behaviour, but the step
belongs alongside any number quoted from it.

## Test coverage where the next paper needs it

`Tests/PureComplexes.wlt` goes 141 → 180; the suite is **238 green**. The counters and exact
samplers were already the best-covered code in the package, while every observable the combinatorics
work actually reports — `SpectralDim`, `HausdorffDim`, `ConnectedComplexComponents`,
`KpathConnectedComponents`, `FractionInLargestKPathComponent`, `PureComplexAutomorphismGroupOrder` —
sat at **zero tests**.

Expected values are known mathematics rather than recorded behaviour: `S_4` on the tetrahedron
boundary, the octahedral group's 48, `b = (1,2,1)` on the torus, `b = (1,1,0)` on the Klein bottle.
Writing them is what found the two defects above.

The exercise also caught a pre-existing test passing for the wrong reason: `fst1` is 3×3, so
`FractionInLargestComponent[fst1]` was reading the facet list as a connected weighted adjacency
matrix and returning the right answer by coincidence.

## `EnsembleWeights.md` — the three ensembles are related exactly

New specification. Each isomorphism class `C` contributes `n(C)!/|Γ(C)|` vertex-labeled objects and
`M!/|Γ_F(C)|` facet-labeled ones, where `Γ_F` is the image of the vertex automorphism group acting
on facets — a different group from `Γ`, and the distinction is the whole point.

As weights over classes: unlabeled is uniform, facet-labeled carries a bounded `1/|Γ_F|`, and
vertex-labeled carries `n!/|Γ|`, factorial in a varying vertex count. So the facet-labeled and
unlabeled ensembles converge as the facet count grows and the vertex-labeled one cannot, with

    NumFacetLabeledPureComplexes[p, M] / (M! NumUnlabeledPureComplexes[p, M])  ==  E_U[1/|Aut_F|]

giving the rate from two counter calls and no Monte Carlo. Validated against 2000 draws
(0.5236 sampled against 0.5308 exact at p = 3, M = 5).

`FacetLabeledCount.md` also gains a correction: its derivation named only two of the four tableau
families in play — columns separating or arbitrary, rows covering or padded — and equations (3.1)
and (3.6) each paired a mismatched two. The shipped code was always right; the prose was not.
