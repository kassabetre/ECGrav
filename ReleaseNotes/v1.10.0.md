# ECGrav 1.10.0 — the correlation-time run length is finally settable

The correlation-time routines sized their measurement run as
`Min[5*eqlT, $ECGravMaxCorrelationSweeps]`. The cap was a setting. **The multiplier was a
literal** — and since `Min` takes the smaller of the two, the literal is what bound on every run
short enough to care. `$ECGravCorrelationRunMultiplier` is now the other half of that pair.

**No result changes.** The default is 5, the value the multiplier was hard-coded to, so every
correlation time this package has ever measured comes out the same. Minor rather than patch only
because it adds a public setting: no function was removed and no argument order changed. Requires
Wolfram Language 15.0+, unchanged.

---

## ⚠️ Read before upgrading

**Nothing you have measured moves, and nothing you have written breaks.** At the default the run
length is identical sweep for sweep. The only user-visible change on an untouched configuration is
the wording of the two `::shortrun` messages.

**If you have ever raised `$ECGravMaxCorrelationSweeps` and seen no change, this is why.** You were
almost certainly on the side of the `Min` the cap does not control, and the old message told you to
raise the cap — the only advice it could give.

---

## The gap

```wl
numsweeps = Min[5*eqlT, $ECGravMaxCorrelationSweeps];
```

At the default cap of 1000, `5*eqlT` is the smaller term for **every `eqlT` below 200**. Short
runs are exactly the ones at risk of failing to resolve the correlation time they report — and
they are precisely the ones where the cap has no effect whatsoever. A user who hit `::shortrun`,
followed its advice, and raised the cap got back a byte-identical run.

The run length is now:

```wl
numsweeps = Ceiling[Min[$ECGravCorrelationRunMultiplier*eqlT, $ECGravMaxCorrelationSweeps]];
```

across all six routines — the four `GraphComputeCorrelationTime` overloads and both
`RandomPureSimplicialComplexMCMCCorrelationTime` overloads.

## Telling which half is binding

Both `::shortrun` messages ended in *"raise the latter"*, meaning the cap. That is now wrong
whenever the multiplier is what set the run, so they name both settings and give you the test:

> The run length is the smaller of `5` times the equilibriation time and
> `$ECGravMaxCorrelationSweeps` (currently `1000`); raise whichever of
> `$ECGravCorrelationRunMultiplier` and `$ECGravMaxCorrelationSweeps` is the binding one — the run
> of `155` sweeps was capped if that equals `1000`, and set by the multiplier if it does not.

The multiplier is message slot 3, so it also reports the value actually in effect rather than a
hard-coded 5. That slot and the run length are the same quantity written twice per routine, twelve
literals in all; a test on each side checks the message argument as well as the sweep count,
because the two drifting apart would make the message misreport the very setting it tells you to
raise.

## Why the run length is rounded up

A multiplier, unlike a sweep cap, invites a fractional value — and a fractional one broke more than
tidiness. The lag range is `numsweeps - 10`, handed to

```wl
LazyCorrelationTime[observable_List, lastLag_Integer, ...]
```

A non-integral run length does not match `lastLag_Integer`, so the call returns **unevaluated** and
is then indexed as though it were an association: a failure a long way from its cause. `Ceiling` is
a no-op at every integer multiplier, so nothing pinned moves, and it rounds up so no setting can
ask for fewer sweeps than it names. `2.5` at `eqlT` 31 gives 78 sweeps, not 77 and not an error.

## Setting it

Plain assignment, like the other two settings:

```wl
$ECGravCorrelationRunMultiplier = 20;
```

It is kept out of the blanket `ClearAll` that runs on package load, so re-loading in a live session
does not silently discard it; it stays assignable after the blanket `Protect`; and
`SyncParallelSettings` pushes it to the subkernels alongside `$ECGravMaxCorrelationSweeps`, so a
parallel driver does not quietly fall back to the subkernel's own default.

## How this was verified

Sweep counts taken by a recording operator that counts the sweeps a run actually performs, at
`eqlT` 31:

| multiplier | cap | graph | complex |
| --- | --- | --- | --- |
| 5 (default) | 1000 | 155 | 155 |
| 10 / 12 | 1000 | 310 | 372 |
| 2 / 3 | 1000 | 62 | 93 |
| 2.5 | 1000 | 78 | 78 |
| 10 / 12 | 100 / 60 | 100 | 60 |

The last row is the cap still winning where it is the smaller — the behaviour this release does
not change.

Every new test was run against the unfixed code, where **exactly three fail**, each for its own
reason: the graph-side run-length test returns `{155, 155, 155, 155, 100}` for
`{155, 310, 62, 78, 100}` — the multiplier ignored, the cap still working; the complex-side one
additionally reports a stale `5` in the message; and the parallel-settings test finds the setting
never arrived on the subkernel, checked through `OwnValues` there rather than
`ParallelEvaluate[sym]`, which inlines the master's value and would report success either way.

The suite is at **190 tests**, all passing.

## Install

```wl
PacletInstall["/path/to/ECGrav-1.10.0.paclet"]
```
