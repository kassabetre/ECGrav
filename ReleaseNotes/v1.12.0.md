# ECGrav 1.12.0 — the MBAR free-energy solve, rebuilt on one shared matrix

`ComputeMinusBetaTimesFreeEnergy` is the self-consistency iteration that *produces* the
`minusBetaF` every other MBAR routine consumes. It was the most expensive thing left in the
package — `O(K^3 N)` interpreted work per iteration, iterated to convergence — and 1.11.0 did not
touch it. On a real 11-beta, 999-sample run it took **218 seconds on eleven kernels**. It now takes
**0.378 seconds on one**.

Its convergence test is replaced at the same time, and **that part changes your numbers**.

---

## ⚠️ Read before upgrading

**Free energies computed by earlier releases are under-converged by about `1e-4`.** The old
stopping rule reported success roughly twelve times short of the accuracy it appeared to promise.
Anything downstream — schedules, reweighted observables, the plots built from them — shifts by a
correspondingly small amount. Nothing was *wrong*; it was less converged than it claimed.

**Regenerating is cheap and worth it.** If you have a stored `GraphMultiHistogram` or
`GraphCTLSchedule` output, its `minusBetaF` can be recomputed from the chart in under a second
without re-running any Monte Carlo:

```wl
ComputeMinusBetaTimesFreeEnergy[hist[[2, All, "data", All, 3]]]           (* beta ladder   *)
ComputeMinusBetaTimesFreeEnergy[hist[[2, All, "data", All, 4]], bt]       (* external field *)
```

**No signature changed**, nothing was removed, and no new setting was added. Requires Wolfram
Language 15.0+, unchanged.

---

## 1. The target loop collapses

Write `A[[s,j]]` for the reduced potential of sample `s` at state `j`. Each pass is

```
    L[s] = LogSumExp_j (logn_j - F_j - A[s,j])
    F_k  = LogSumExp_s (-L[s] - A[s,k])
```

The second line is the point. The term carrying the target `k` is `beta_k*E_s`, which *is*
`A[s,k]` and has no `j` in it — so it factors straight out of the inner `LogSumExp`, and the outer
loop over targets collapses into one column-wise reduction. `A` does not depend on `F` either, so
it is built once and reused across every iteration.

All three overloads now build `A` and hand it to a shared `MBARSolveFreeEnergies`:

| overload | `A[[s,j]]` |
| --- | --- |
| beta ladder | `beta_j * E_s` |
| scalar external field | `bt * h_j * O_s` |
| vector external field | `bt * (h_j . O_s)` — the matrix `MBARWeightBasis` already forms |

Measured on an actual `GraphCTLSchedule` output, K = 11, N = 999: **218.2 s on eleven kernels →
0.378 s on one.** The two external-field overloads agree to exactly `0.0` on the same
one-dimensional data written as scalars and as one-element vectors.

## 2. The convergence test was gauge-dependent

The old rule was `Sqrt[Sum[(1 - F_k/Fnew_k)^2]]`. Free energies are defined only up to an additive
constant, so `F_k` in that denominator is an arbitrary number — the test depended on a gauge
carrying no physical meaning. The same converged iterate, three gauges:

| gauge | old test | new test |
| --- | --- | --- |
| mean-zero (what the code uses) | `2.4e-15` | `1.6e-15` |
| `F_1 = 0` | **`Indeterminate`** — divides by zero | `1.6e-15` |
| shifted by ten | `2.9e-16` | `1.6e-15` |

It also compared the *already* mean-centred `F` against an *uncentred* `Fnew`, so a gauge shift
leaked into the measure.

## 3. And it stopped twelve times short

The iteration contracts at about `0.917`, so the error remaining after a step is `step*r/(1-r)`,
roughly twelve times the step — a ratio constant to three digits across 260 iterations. A rule that
stops on the step size therefore overshoots by that factor.

The new rule is `Max[Abs[Fnew - Mean[Fnew] - F]]` — gauge-invariant, no division, like compared
with like — converged against a geometric extrapolation of the remaining error rather than the raw
step. The tolerance now means what it says:

| stopping on | tolerance | true error |
| --- | --- | --- |
| the raw step | `1e-8` | `1.2e-7` |
| **the error estimate** | `1e-8` | **`9.8e-9`** |

The default tightens from `1e-5`/`1e-6` to **`1e-8`**, which the rewrite makes free: `1e-6` costs
0.27 s, `1e-8` 0.37 s, `1e-10` 0.49 s, `1e-12` 0.56 s. Five orders of magnitude of extra accuracy
roughly doubles the runtime. Under the old implementation that same tightening would have gone from
218 s to well over 400 s, which is presumably why the tolerance was loose to begin with.

## How this was verified

- **Against the literal definition.** The nested sum is written out independently in the test and
  iterated a fixed number of times rather than to a tolerance, so it exercises the algebra rather
  than a refactor of itself.
- **Against a real run.** The rewritten solve reproduces an independent 2000-iteration reference on
  the 11-beta fixture to `9.8e-9`, and reproduces the *stored* `minusBetaF` from that run — what the
  old code actually returned — to `1.9e-14` when run under the old stopping rule. The `1e-4` gap
  reported above is the old rule stopping early, not a change of answer.
- **Cross-overload.** The scalar-field and vector-field overloads agree to exactly `0.0` on the same
  data expressed both ways.
- **Revert-and-fail, which caught a vacuous test.** The first draft compared the two field overloads
  at `bt = 1`, where deleting the `bt` factor is the identity — and the suite passed with that break
  deliberately in place. It now compares at `bt = 1.7` with explicit `bt`-sensitivity legs, and the
  same break fails it.

The suite is at **195 tests**, all passing.

---

## Also noted, not changed

The solve still returns silently when it hits its 30 000-iteration cap without converging. The
returned error estimate makes that detectable by the caller, but nothing warns. Worth a message.

## Install

```wl
PacletInstall["/path/to/ECGrav-1.12.0.paclet"]
```

Requires Wolfram Language 15.0+, unchanged from 1.7.0.

Upgrading in a running session needs a `Quit[]` first — `Needs` is a no-op while `` ECGrav` `` is
already in `$Packages`, so the kernel keeps the old definitions.
