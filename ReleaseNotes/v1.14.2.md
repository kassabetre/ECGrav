# ECGrav 1.14.2 — sweeping the facet order is 12–27× faster

A performance release. **No value that any call returned has changed.**

The cycle-type sum behind `NumFacetLabeledPureComplexes` depends on the facet order `M` only
through a falling factorial. The cycle types themselves, their `N` values and their weights do
not — but every call rebuilt all of it from scratch, including the long-cycle table, the
factorials and the partition data. That is exactly backwards for the way the function is actually
used, which is a sweep over `M` at one purity and vertex count.

## What changed

The `{N, weight}` pairs are now collected once per `(p, n)`, memoised, and shared across every
facet order. Equal `N` are merged as the table is built — different multiplicity vectors often
reach the same `N` — which shrinks the sum by a further **1.5× at p=2, 2.3× at p=3, 2.9× at p=4**.

Over `M = 1…60`:

| `(p, n)` | before | after | |
| --- | --- | --- | --- |
| (2, 30) | 0.252 s | 0.020 s | **12.6×** |
| (3, 30) | 1.181 s | 0.059 s | **20×** |
| (4, 30) | 3.939 s | 0.145 s | **27×** |

A repeated scalar call at the same `(p, n)` goes from 0.0397 s to 0.00068 s — a factor of 59.

The memo is released by ``ECGrav`Private`NumPCClearCache[]``, which now lists
`NumFLPCWeightTable`. `FacetLabeledCount.md` §5 used to record that nothing here was memoised;
that is no longer true and the section says so, with the reason.

## New: a list form

```wl
NumFacetLabeledPureComplexes[p, Mlist, n]
```

gives the count for each facet order in `Mlist` at one vertex count, elementwise identical to
mapping the three-argument form over `Mlist`, with the guards applied per entry. It is **not**
faster than the memoised scalar form — it is the same machinery — but it states the intent and
does not depend on the memo surviving a cache clear.

## Verification

Elementwise against the **previous** computation path, reconstructed from `NumFLPCTSum` so that
the comparison is genuinely before-versus-after rather than the new code checking itself:

- **468 scalar parameter sets** across `p = 1…4`, `M = 0…8`, `n = 0…12` — zero mismatches,
  degenerate corners included.
- **52 list-form sets**, elementwise against the same reference.
- The 93-digit `NumFacetLabeledPureComplexes[3, 50, 10]` unchanged.

Seven new tests pin the vectorised path, the degenerate corners, that clearing the memo cannot
change a value, that `NumPCClearCache[]` actually reaches the new table (or the memo leaks), and
that merging equal `N` reproduces `NumFLPCTSum` term for term. Suite 238 → 245.

## Also

`FacetLabeledCount.md` §9, previously "What is *not* available: a recurrence", is retitled and
extended with the two recurrences that **do** exist for the non-separating count `B`:

- a constant-coefficient recurrence in `M`, read off the closed form, whose characteristic roots
  are the distinct `N(λ,p)` — and which does not pass to the separating count, since that has the
  falling factorial in place of the power;
- a dynamic programme on content vectors that never forms a cycle type and which, composed with
  the Stirling inversion of (3.6), computes `s_F` **with no Burnside average anywhere**. That is
  the only route to the facet-labeled count recorded there which avoids Burnside, and as a wholly
  independent derivation it is a stronger check on the shipped algorithm than any single leg of
  §10.

Requires Wolfram Language 15.0+, unchanged.
