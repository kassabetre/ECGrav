# ECGrav 1.8.1 — the energy-callback check rejected correct hamiltonians in external-field runs

`GraphCTLSchedule`, `GraphMultiHistogram` and `GraphParallelTempering` returned `$Failed` with
`ECGrav::badham` on hamiltonians that were written exactly the way those functions require. The
run died at the gate, before doing any work, telling the user their callback was unusable when it
was not.

Bug fix only. **No public function was removed, no argument order changed, no new setting**, and
no result that previously computed changes value. Requires Wolfram Language 15.0+, unchanged.

---

## ⚠️ Read before upgrading

**If you run any driver over a table of external field values, this bug affects you on 1.7.0,
1.7.1 and 1.8.0.** The check was introduced in 1.7.0. There is nothing to re-run and no result to
distrust — the failure is loud and total, not silent: affected calls returned `$Failed` and
produced no data at all. If your external-field runs have been completing, you were never hitting
it.

---

## What went wrong

In an external-field run, the callbacks' parameters are **a row of the field table, not
`hparams`**. The driver applies the head to a row —

```wl
Apply[hamiltonian, externalFieldTable[[i]]]
```

— and `hparams` is empty, because the only parameter *is* the field. So a hamiltonian written the
way those drivers require, `h[am_List, f_Real]` passed as `h[]`, is ultimately called as
`h[graph, field]`.

The usability probe ran before that Apply, using the empty `hparams`, and so evaluated
`h[graph]` — which comes back unevaluated, is not a number, and was reported as an unusable
callback.

On a reported 8-vertex `GraphCTLSchedule` over five `NT0` values:

```
h[seed, -0.5]  ->  310.             numeric: True     <- what the driver actually calls
h[seed]        ->  h[{{0,0,1,…}}]   numeric: False    <- what the probe checked
```

**Eight probe sites now pass a real field row:** the `externalFieldTable` overloads of
`GraphMultiHistogram` (2) and `GraphCTLSchedule` (4), and the two external-field
`GraphParallelTempering` overloads that take replicas from a previous run, where the row comes
from `inputReplicas[[1,"externalField"]]`.

**The beta-tempering overloads are untouched.** There `hparams` really is the parameter list, and
their probes were always correct. The distinction is exactly whether the driver takes the
callbacks' parameters from the field table or from the user's `head[params]`.

## Testing

**177 tests, all passing** (`wolframscript -file Tests/ci-run.wls`, ~70 s).

One is new. There were **no tests on this check at all**, which is why the bug shipped in the
first place. `EnergyCallbackProbe-external-field-arity` pins the contract at the probe rather than
through a driver — the drivers equilibrate before they return anything, which is minutes, and the
probe is where the contract lives. It asserts that the field-row arity is accepted, that the old
`hparams` probe rejects it so the test cannot pass vacuously, and that an undefined head is still
rejected, so the fix did not simply defang the check.

It also records one limit rather than hiding it: a slot-based pure `Function` ignores extra
arguments, so it satisfies this probe and is caught one level in, by the inner driver's own probe
on the applied form.

The fix was verified end to end by running the reporter's notebook unmodified in a fresh kernel.
It now completes and returns the documented result — the external-field schedule across six
replicas plus the multi-histogram association — with no `ECGrav::badham` and no `ECGrav::baddelh`.

Download `ECGrav-1.8.1.paclet` below, then:

```wl
PacletInstall["/path/to/ECGrav-1.8.1.paclet"]
```

already in `$Packages`, so the kernel keeps the old definitions.
