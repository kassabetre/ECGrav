# ECGrav 1.11.1 — GraphParallelTempering rejected correct hamiltonians

Feeding a schedule straight from `GraphCTLSchedule` into `GraphParallelTempering` failed. Both
schedule-driven overloads returned `$Failed` with `ECGrav::badham` before doing any work, rejecting
a hamiltonian written exactly the way those drivers require:

```wl
GraphParallelTempering[seed, bt, h[], dH[], sched[[2 ;; 3]], conjObs, obs, NN, unlabeled, minE]
```

A one-line fix at two sites. No public function was removed, no argument order changed, no new
setting. Requires Wolfram Language 15.0+, unchanged.

---

## ⚠️ Read before upgrading

**Nothing you have measured is wrong.** This bug *refused to run*. It fired before the driver
touched a replica, so there is no run that completed with bad numbers — only runs that never
started. If your tempering worked, it worked.

**Present since 1.7.0.** The callback gate was introduced in `bdf12d6` (v1.7.0) and 1.8.1 fixed its
arity in the external-field drivers. These two sites were not among them, so **1.7.0 through 1.11.0
are all affected**.

**You are affected if** you pass the hamiltonian as an inert head — `h[]`, with
`h[am_List, f_Real] := …` — to the seed-graph form of `GraphParallelTempering` together with a
schedule. That is the form the schedule-driven overloads require, so in practice it means anyone
handing `GraphCTLSchedule` output to `GraphParallelTempering`, in single-field runs and in the
homogeneous `c·O` recipe alike. The continue-from-replicas overloads were already correct.

---

## The bug

The two schedule-driven overloads (`MCSims.wl:7880` with `delH`, `8178` without) take the callback
parameters from a replica's field **label**:

```wl
Apply[hamiltonian, replicaSwapEdgesLabels[[2, Key[i]]]]
```

That is a **third** calling convention, alongside `hparams` (the beta-tempering overloads) and the
field table (`GraphMultiHistogram`, `GraphCTLSchedule`). Their gates nonetheless probed with
`hparams`, which is *empty* when the hamiltonian is passed as `h[]`. So the probe evaluated
`h[graph]`, which does not match `h[am_List, f_Real]`, came back unevaluated, and `NumericQ` said
no.

This is the same defect 1.8.1 fixed elsewhere, in the one convention that fix did not cover.

Both gates now probe with `Sequence@@replicaSwapEdgesLabels[[2,1]]` — the first replica's label,
positionally, matching how the continue-from-replicas overloads already read
`inputReplicas[[1,"externalField"]]`.

---

## How this was verified

- **All 24 gate sites audited** against how their own driver actually invokes the callbacks.
  Exactly these two disagreed. The beta-tempering paths really do use `hparams`; the external-field
  histogram, schedule and continue-from-replicas paths were already correct.
- **Reproduced against a real 11-replica schedule** before the fix and after. The gate now receives
  the head plus the field value, and both overloads run to completion instead of returning
  `$Failed`.
- **A new regression test pins the CALL SITE**, which is the gap this fell through.
  `EnergyCallbackProbe-external-field-arity` pins the *probe* — deliberately, since the drivers
  equilibrate before returning anything — and so proves the probe behaves correctly *given* the
  right arguments, while nothing checked that a driver *hands* it the right ones. The new test
  stubs both probes so the gate fails on purpose and the driver returns before equilibrating,
  then asserts the field value reached the probe at all.
- **Revert-and-fail.** Against the unfixed code all three legs of the new test return `False`,
  and the suite reports exactly one failure. It cannot pass vacuously.

The suite is at **194 tests**, all passing.

---

## Also noted, not changed

The gate is checked once per driver call rather than per sweep, which is why a wrong probe costs a
whole run rather than a slow one. The trade is deliberate — one probe is nothing next to a Monte
Carlo run — but it does mean the probe's argument list has to match the driver's calling
convention exactly, and there are now three of them. The audit above is the guard; a fourth
convention would need its own call-site test.
