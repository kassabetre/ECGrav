# ECGrav 1.8.0 — the facet-labeled draw weighed every candidate when a handful would do

`RandomUniformFacetLabeledPureSimplicialComplex` is **2–103× faster**. At `{p,M,n} = {4,8,20}` a
sample went from 52.8 ms to 0.51 ms; at `{3,15,30}`, from 108 ms to 1.24 ms.

Nothing about the output changed. Same distribution, same shape, **no public function added,
removed or renamed, no argument order changed, no new setting**, and the Wolfram Language 15.0+
requirement is unchanged from 1.7.0.

---

## ⚠️ Read before upgrading

**Seeded runs do not carry across 1.7.1.** The draw makes a different number of `RandomChoice`
calls per sample, so a given `SeedRandom` produces different complexes. The *distribution* is
unchanged — verified against exact class enumeration at 60,000–100,000 draws per parameter set —
so any statistic you compute from a batch is unaffected. Only pinned per-seed values move.

**Calls of 100–2000 samples now run serially.** `$RandomFacetLabeledParallelThreshold` moves from
100 to 2000; see below for why that is a speedup rather than a regression. Nothing about it is
public and no result changes, but if you were counting on subkernels being busy, they will not be
until 2000 samples.

---

## What changed

**The draw groups candidates by completion key.** Each facet was chosen by weighing every
admissible candidate separately against the number of ways the rest of the complex could still be
finished. At `{4,6,15}` that is 441 candidates for each of 6 facets, and it was essentially the
entire cost of a sample.

But a candidate's weight enters **only** through `nu(uncovered \ S)` — a multiplicity vector of
block sizes summing to at most `p`. The number of distinct such vectors is at most
`Sum[PartitionsP[i], {i, 0, p}]`: **4 at `p=2`, 7 at `p=3`, 12 at `p=4`**, however many hundreds
of candidates there are. Those 441 candidates at `{4,6,15}` carry **3** distinct keys.

So the draw now picks a key group with weight (group size) × (completions), then a member of that
group uniformly. Members of a group have equal weight, so this is the same distribution — with a
handful of memo lookups per facet instead of one per candidate.

Two supporting pieces. The key rides as a base-`(p+1)` integer code, which packs it without
carrying because each entry is at most `p`, so `Tally` on a packed integer array does the grouping
in one pass. And the codes are **updated in place** rather than recomputed: when a facet covers a
block for the first time, exactly the candidates containing that block lose it from their
intersection with the uncovered set. The per-cycle-type tables behind this live in a new private
`RandFLPCCandTable`, memoised and released by `NumPCClearCache` with everything else.

**`$RandomFacetLabeledParallelThreshold` raised from 100 to 2000.** This is a consequence of the
above rather than an independent tuning change. What the parallel branch pays is *fixed* rather
than per-sample — `DistributedContexts` ships the whole of `` ECGrav`Private` ``, memo tables
included, on every call, so the cost even grows as those tables fill. Cutting the serial cost by
20–100× moved the crossover out with it, and at 100 samples the parallel branch had become a
**3–16× pessimisation**. Remeasured on 11 subkernels with kernels up and tables warm, the
crossover now runs 200 samples at `{2,3,4}`, 300 at `{2,4,6}`, 800 at `{3,6,12}`, 1700 at
`{4,6,15}`, 2800 at `{3,10,20}` and past 3200 at `{4,8,20}`.

No single constant is right everywhere, and the penalties are lopsided: too low costs up to 16×,
while too high costs at most the parallel speedup, which is only 2–3× anywhere near the crossover.
The constant therefore sits at the top of the measured range rather than the middle. At 2000 the
serial/parallel ratios run 0.87–2.34; by 5000, 1.49–3.48.

## Testing

**176 tests, all passing** (`wolframscript -file Tests/ci-run.wls`, ~70 s).

One is new. A wrong key would still emit perfectly plausible complexes drawn from the wrong
distribution — the failure mode this package has been bitten by before — so
`RandFLPCCandTable-keys-track-uncovered` checks the two invariants the grouped draw rests on
**directly against the definitions they replace**, rather than through the output: that the packed
candidate table lists exactly the admissible facets, and that the incrementally updated codes
still decode to `nu(uncovered \ S)` after any sequence of facets has been laid down. It runs over
every cycle type that can occur with `p <= 4`, `n <= 11`.

It was also confirmed to **fail** under two injected defects — a wrong packing radix, and codes
never updated — before being trusted. A differential test that cannot fail is worse than no test.

The existing checks carry the rest: the Burnside weight identity
`Total[weights] == n! NumFacetLabeledPureComplexes[p,M,n]`, exactly, on 10 parameter sets, and
chi-square over exhaustively enumerated classes.

## Note — an alternative that was measured and rejected

A rejection-free **dynamic program over row-type multiplicities**, carrying the current
column-equality partition as part of its DP state so that separation is conditioned on rather than
tested for, was evaluated as a replacement for this sampler.

It is correct: its counts agree with `NumFacetLabeledPureComplexes` on all 234 triples with
`p <= 4`, `M <= 6`, and it is uniform. But it is exponential where this sampler is polynomial. Its
state space is `2^M (n+1) (p+1)^M Bell(M)`, and because `n <= pM` the only free axes are `p` and
`M` — both exponential. Its table costs 9.7 s and 164 MB at `{3,6,12}`, 118 s and 1.8 GB at
`{3,7,14}`, and did not build in 180 s / 4 GB at `{3,8,16}` — where this sampler now draws in
0.27 ms.

As a *counting* method it loses by ~33,000× for a structural reason: the falling-factorial weight
in `NumFacetLabeledPureComplexes` already performs the Möbius inversion over the partition lattice
in closed form, which is exactly what the partition state re-derives by brute force. Section 11 of
`FacetLabeledSampler.md` records the measurements.

The one thing that came out of the exercise is this release: at `p >= 3` the DP's *per-draw* cost
was below `RandFLPCOne`'s, which said nothing about the DP and everything about where this
sampler was spending its time.

## Install

Download `ECGrav-1.8.0.paclet` below, then:

```wl
PacletInstall["/path/to/ECGrav-1.8.0.paclet"]
```

Requires Wolfram Language 15.0+, unchanged from 1.7.0.

Upgrading in a running session needs a `Quit[]` first — `Needs` is a no-op while `` ECGrav` `` is
already in `$Packages`, so the kernel keeps the old definitions.
