# ECGrav 1.11.0 — the CTL metric, rebuilt from one shared MBAR weight vector

Building the thermodynamic metric was the dominant cost of a multi-field `GraphCTLSchedule`, and it
grew as the **square** of the bootstrap table. With one external field that was a few seconds and
nobody noticed. With two it was over seven hours, which is not a slow schedule but an impossible
one — the run does not finish, it gets abandoned.

It is now a fraction of a second. **The schedules are unchanged**: this is an algebraic identity,
not a new approximation, verified to 2e-14 against the code it replaces. No public function was
removed, no argument order changed, no new setting. Requires Wolfram Language 15.0+, unchanged.

---

## ⚠️ Read before upgrading

**Nothing you have built needs regenerating.** Unlike 1.10.1, this release does not change what a
schedule *is*. The numerics agree with 1.10.1 to machine precision on targets inside and far
outside the sampled box, and the one deliberate behavioural change — see §4 — was measured to alter
**0 of 441** density-mask verdicts at every bootstrap size tried.

**One visible difference**, so it does not look like a bug: the progress message during a schedule
build now reports a larger number of sample points. It always collected that many. The old message
computed `numInterpolatingSamples^numVars` while the grid is built by widening the bootstrap box
20% each way at the *unwidened* step — so at two tempered components it said 400 and collected 841.

**`General::munfl` messages during a schedule build stop.** `ExtrapolatedExpectationValue` divided
by raw MBAR denominators, which underflow once the target field moves away from the sampled ones —
which is exactly what an interpolation grid over the bounding box asks it to do. Every output is a
ratio of the weights, so they are now formed in log space and shifted by their own maximum before
exponentiating. The answers were never wrong; they were reached expensively and noisily.

**A stalled build that used to sit on "Distributing definitions" was not deadlocked.** That panel
was `ParallelTable`'s, and coarse-grained chunking meant nothing returned until a whole chunk
finished. The metric pass is serial now, so the panel is gone.

## 1. The free energy cancels, so it is not computed

Write `D_s(x)` for the log MBAR denominator of sample `s` at target field `x`. Setting
`u_s = Exp[-D_s(x)]`, an extrapolated expectation value is

```
    (v . u) / Total[u]
```

— an ordinary weighted mean. The free energy that `ExtrapolatedExpectationValue` used to obtain
through a full `NegativeBetaTimesFreeEnergy` call, itself as expensive as the sum that followed it,
is only the normaliser of `u`, and it divides straight back out of the ratio.

## 2. One weight vector serves every grid

`u` depends on the target field and on nothing else — it has no knowledge of which observable is
about to be averaged against it. The schedule builder was filling
`numVars(numVars+1)/2` second-moment grids, `numVars` first-moment grids and one effective-sample-
size grid — **six** at two tempered components — each re-deriving the same denominators from
scratch. They are now one pass.

## 3. The expensive part does not depend on the target at all

```
    D_s(x) = beta x.O_s  +  Log[Sum_j Exp[Log[n_j] - F_j - beta h_j.O_s]]
```

The term `beta x.O_s` carries no `j`, so it factors out of the sum. What remains — the whole sum
over the `K` bootstrap field points, the only part quadratic in `K` — has no `x` in it, and is
built **once for the entire grid** instead of once per grid point per observable. Per point, all
that is left is one matrix–vector product.

Measured against 1.10.1, same fixture, same code path, serial, six quantities at 25 grid points:

| bootstrap table | 1.10.1 | 1.11.0 |
| --- | --- | --- |
| K=16, N=120 | 24.18 s | 0.072 s |
| K=25, N=100 | 47.94 s | 0.078 s |
| K=49, N=100 | 180.76 s | 0.269 s |
| K=100, N=100 | 767.50 s | 1.215 s |

Scaled to the real 841-point grid, the 1.10.1 column is **7.2 hours** at K=100. The schedule builder
amortises the basis across the grid on top of that.

## 4. The effective-sample-size interpolant is gone

`rho` now evaluates the MBAR effective sample size **exactly**, at 0.107 ms a call — affordable
only because of §3.

**This changes no schedules, and it was not a bug.** `densityPoints` steps by the same increment as
the interpolation grid and merely starts four steps inside it, so its points coincided with
interpolation *nodes* to 9e-16, where `Interpolation` reproduces what it stored. Measured: 0 of 441
mask verdicts differ.

It goes because that correctness rested entirely on a coincidence between two grid definitions
written in different places, with nothing recording the dependency. Evaluated *off* node — which
any change to either grid would cause — the interpolant disagrees with exact ESS about the mask at
246 of 4000 points, about half of them false masks punching holes through the supported region, and
returns negative values at 43, meaningless for a Kish count bounded below by 1. Lowering the
interpolation order does not help; the surface spans two orders of magnitude across the grid.

## How this was verified

- **Against the code it replaces**, inlined so the two share nothing: first moments, second moments,
  the free energy and the effective sample size, at four target fields — agreement to **1e-15**.
  One of those targets sits at an effective sample size of 2.01, meaning two samples carry
  essentially all the weight, which is the deep-extrapolation corner the log-space shift exists for.
- **The matrix moment form against the public entry points**, 343 comparisons, max relative
  difference **4.2e-15**.
- **Against a closed-form fixture** where the density of states is `MVN(0,Sigma)` under reduced
  potential `c.O`, so samples at field `c` are `MVN(-Sigma.c, Sigma)`, `minusBetaF = c.Sigma.c/2`
  in closed form and `E[O](x) = -Sigma.x` exactly. This tests the reweighting, not just the refactor.
- **End to end**: an 8-replica schedule on a K=16, N=120 fixture completes in 20 seconds, where
  1.10.1 had not finished the metric build in ten minutes.

The suite is at **193 tests**, all passing.

## Also in this release

Four specifications, none of which change any code:

- **`MBARWeights.md`** — the algebra above in full, with the reference implementation, the cost and
  verification tables, and an implementation map.
- **`HomogeneousHamiltonian.md`** — how to temper in inverse temperature *and* an external field at
  once with the shipped API, by writing the hamiltonian in homogeneous form so beta becomes one of
  the tempered couplings. Includes the units caveat, which is the part most easily missed: recorded
  energies become `c.O = beta*H_phys`, consistent within a replica and meaningless across replicas
  once beta varies.
- **`FacetLabeledCount.md`** — the specification of `NumFacetLabeledPureComplexes`, the last of the
  four pure-complex counters and samplers without one.
- Refreshed line anchors throughout the pure-complex specifications, and a corrected `p = 2`
  counterexample in `UnlabeledCount.md` §2.1 where the old text gave a `p = 3` one.

## Also noted, not changed

**`essFloor` is still `essMinFraction * Total[...]`,** a flat fraction of the total sample count.
Its meaning therefore drifts with the size of the bootstrap table: at K=20 it keeps 9.8% of the
interpolation box where a K-independent floor of `0.5*N` keeps 5.0%, while at K=400 it keeps 23.5%
against 36.6%. Refining a bootstrap grid silently redefines what counts as "supported" by about
1.5x. This is a wart, not a cliff — the kept fraction is stable at 22–24% from K=48 to K=400,
because the effective sample size grows with K as neighbouring replicas start to overlap.

**The scalar `bf_Real` overloads** of `ExtrapolatedExpectationValue` and
`NegativeBetaTimesFreeEnergy` are the beta-tempering path and are untouched. They were never the
bottleneck.

**None of this helps a frozen chain.** If a bootstrap run reports `GraphEquilibriate::noconv`, or a
correlation time comparable to the run length it was measured over, the metric is being built from
data that is not from the target distribution. A faster wrong answer is still wrong.
